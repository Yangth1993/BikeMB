当前运行路径

工程同时保留 Arduino 验证路径和 ESP-IDF 迁移路径。Arduino 仍是基础回归路径；ESP-IDF 路径已经承接双核运行模型、AudioSession、Wi-Fi 和云端语音 transport，用户已确认基础录音和回复正常。

默认路径：Arduino

入口在 main.cpp 的 setup() / loop()。dashboard、触摸滑动、档位播报、音频自检、直接语音识别以及默认关闭的 AI framework 都走这里。

迁移路径：ESP-IDF

入口在 main.cpp 的 app_main()。当前已把 Runtime/UI/AI/Cloud/Wi-Fi 放入明确的 Core 0/Core 1 运行模型；AudioSession 使用 ESP-IDF I2S，CloudWorker 使用 esp_http_client 调用 Qwen 和 CosyVoice。

Bootloader 与双核启动链路

ESP32-S3 先从芯片 ROM 启动，再进入 Flash 二级 Bootloader。二级 Bootloader 只跳到应用 CPU0 入口；CPU1 由应用侧 CPU0 拉起。

阶段运行核心入口/动作下一跳
ROM 一级 BootloaderCPU0芯片 Mask ROM，不占外部 Flash 分区。加载 Flash 0x000000 的二级 Bootloader。
Flash 二级 BootloaderCPU0bootloader_start.c::call_start_cpu0()bootloader_utility_load_boot_image() 选择、校验并加载应用。
应用早期启动CPU0cpu_start.c::call_start_cpu0()拉起 CPU1，并分派到 start_cpu0_default()。
第二核心启动CPU1cpu_start.c::call_start_cpu1()start_cpu_other_cores() 等待 CPU0 scheduler。
业务入口两核CPU0/CPU1 各自运行 FreeRTOS scheduler；main_task 在 CPU0 调用 app_main()。Arduino 创建 Core 1 loopTask；ESP-IDF 创建 Core 0 bike_runtime 和 Core 1 bike_ui。

同名入口不是同一函数

Bootloader 镜像和应用镜像各自链接一个 call_start_cpu0。前者是二级 Bootloader 入口，后者是应用入口，属于两个独立 ELF。

双核共享一个应用镜像

CPU0 和 CPU1 共享被选中的 BikeMB 应用镜像与地址空间，不是分别烧录两个 app。Bootloader 也不会创建 bike_runtime 或 bike_ui。

当前项目未启用 Secure Boot 和 Flash Encryption。Bootloader 的镜像结构/checksum/hash 校验不能当作 BikeMB 签名身份验证；未来启用安全启动时需要单独设计密钥、烧录和恢复流程。
正式音乐开发门禁：完成 ESP-IDF 双核迁移并通过 ADR-0004 验收后，才能开始正式 MusicService、产品音乐流和点歌开发。门禁关闭前只允许隔离的 decoder/HTTPS stream spike、接口和 mock。
ADR-0004 验收项完成标准
任务归属bike_runtime 固定 Core 0，bike_ui 固定 Core 1；产品路径由 BikeMB app_main() 启动。
UI 与跨核通信LVGL 只在 bike_ui 访问，其他 task 使用 queue/event/snapshot。
AI/音频迁移AI、Cloud/Wi-Fi、AudioSession 和语音由 ESP-IDF runtime/service 管理，不依赖 Arduino setup()/loop()。
验证证据双核 build/test 和板级启动、触摸、显示、录音、TTS、取消回归通过，并记录 heap、PSRAM、stack、UI 延迟和 underrun 基线。

取消与旧结果隔离

取消或忙态重新按键会递增有效 requestId，旧 callback 不能改写新状态；但阻塞中的 HTTPS 只能等待 15 秒读超时返回。

BOOT 安全边界

GPIO0 仍是 ESP32-S3 启动 strap。3 秒延时只阻止应用层误触发；按住 BOOT 上电或复位仍可能进入 ROM 下载模式。

当前真实链路使用 Qwen Chat，不是 DeepSeek。真实云测试环境还启用了 insecure TLS，且串口会打印截断的转写/回答；这些都必须在产品启用前收口。

区域简要说明
Bootloader / Partition Table启动链路基础设施。通常不在应用逻辑中直接操作。
nvs适合保存少量持久化数据，例如用户设置、传感器校准、累计里程。
otadata保存 OTA 选择状态，让 bootloader 知道启动哪个 app 槽。
app0/app1两个应用槽。默认布局每个约 6.25MB，比较适合当前 UI + 音频资源验证。
spiffs文件系统区域。后续如果字体/图片不想编译进固件，可以放这里。
coredump保存崩溃信息，辅助排查死机、异常重启。
区域简要说明
app0/app1每个只有 3MB。相比默认布局缩小，是为了给 ESP-SR 模型分区腾出空间。
spiffsESP-SR 布局保留 6MB 文件系统区；当前语音命令验证暂未重点使用它。

ESP-IDF Runtime 骨架

这条路径已经承接产品入口、task/core 归属、UI 跨核事件、ESP-IDF AudioSession、Wi-Fi STA 和 Qwen/CosyVoice 云端 transport。

函数作用
BikeRuntime_Init()创建 event queue，并调用 BoardSupport_Init()。
BikeRuntime_Start()启动 UiService、AI/Wi-Fi/AudioSession 初始化边界和 RuntimeTickTask。
BikeRuntime_PostEvent(...)向固定 FreeRTOS queue 投递事件；队列满时丢弃低优先级 tick。
BikeRuntime_FindServicePlan(...)返回 host-testable 的 task/core 所有权规划。
UiService_Start(...)启动拥有 LVGL 的 UI task。
UiTask(...)初始化 LVGL/dashboard，消费事件，并调用 LvglPort_Run()。
当前仍未满足 ADR-0004：ESP-IDF 云端语音基础录音和回复已由用户确认，但取消、断网/超时异常、长稳资源基线、UI 延迟和 audio underrun 尚未完成验收。正式 MusicService 和点歌因此保持阻塞。

验证入口

当前测试入口是 tools/run-tests.ps1，它会扫描并执行 tools/tests/test_*.py。这些 Python 脚本主要是 contract tests：读取源码、配置和文档中的关键符号，确认模块边界、feature gate、构建环境和架构约束没有被破坏。

目前没有引入 Unity、GoogleTest、Catch2、doctest 这类正式 C/C++ UT 框架。仓库里的 C++ “单元级”测试是 host-side assert tests：由 Python 脚本调用本机 g++ -std=c++17 -Wall -Wextra -Werror 编译纯逻辑 .cpp 和 tools/tests/*_test.cpp，运行后依靠 assert() 判断结果。

当前限制

这些是后续继续开发前需要明确的边界。

音频链路所有权

AudioSession 已统一 AI、Audio Self Test 和 Audio Prompts；Voice Commands 尚未迁移，继续保持编译期互斥。

语音命令能力

voice-direct-test 没有唤醒词，可能误识别；当前 Arduino ESP-SR 路径也还没有启用中文命令识别。

真实云仍是测试配置

真实链路已接入，但使用 Qwen Chat、insecure TLS，并会打印截断后的转写和回答；默认固件仍关闭 AI。

AI 页面暂时只读

dashboard 第二页已经显示网络、状态、提示、波形和状态环；取消、重试、停止动作尚未接到 Assistant 命令接口。

取消和 TTS 延迟

取消不能主动关闭阻塞 HTTPS；CosyVoice PCM 完整缓冲后再播放，PSRAM 峰值和首包延迟仍需优化。

音乐路径未实现

HTTPS MP3 解码器、Stream Player、Music Service 和未来点歌 resolver 仍属于目标架构。

ESP-IDF 第一阶段已接入 AI

AI、Cloud 和 Wi-Fi task 已固定到 Core 0，AI 页面切换经 runtime event 交给 Core 1 UI；AudioSession、Wi-Fi 和 Qwen/CosyVoice transport 已迁入 ESP-IDF，基础录音/回复已确认。
