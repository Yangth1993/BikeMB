# BikeMB 产品路线图

## 路线图原则

- 先稳定核心码表，再扩展交互和音频。
- 每个阶段都应有可验证产物。
- P2 实验功能默认关闭，不能影响 P0 核心骑行显示。

## 阶段 0：硬件 bring-up 基线

状态：已完成基础验证。

目标：

- 验证串口、烧录、LCD、背光、PSRAM 和基础绘制链路。
- 保留 `src/firmware/bringup` 作为硬件验证入口。

验收：

- PlatformIO Core 可用。
- 串口 `COM5` 可通信。
- 屏幕点亮，背光可控。
- 实时 dashboard 可运行。

## 阶段 1：正式 UI demo 基线

状态：进行中。

目标：

- 初始化并稳定 `src/firmware/bikemb`。
- 接入 LVGL。
- 复刻当前 dashboard 的观感和信息结构。
- 明确 UI、数据、输入、存储的模块边界。

验收：

- `src/firmware/bikemb` 能构建并显示 LVGL dashboard。
- 主界面在圆屏上可读。
- `src/firmware/bringup` 不被破坏。

## 阶段 2：基础可骑行 MVP

状态：待启动。

目标：

- 接入真实或可替换的轮速数据链路。
- 显示速度、单次里程、骑行时间、电量和总里程。
- 支持实体按键切换页面。
- 持久化总里程和基础设置。

验收：

- 上电 3 秒内进入主界面。
- 主界面速度为最大视觉元素。
- 停止骑行后速度回落为 0。
- 总里程断电后不丢失。
- 页面切换不阻塞数据刷新。

## 阶段 3：基础设置和产品可用性

状态：待启动。

目标：

- 增加轮径、单位、亮度等基础设置。
- 优化圆屏页面结构。
- 建立更清晰的异常和串口诊断路径。

验收：

- 设置可保存并在重启后恢复。
- 主界面、信息页和设置页之间切换稳定。
- 常见外设异常有串口日志辅助定位。

## 阶段 4：音频和语音实验

状态：实验方向。

目标：

- 默认关闭的音频自检。
- 默认关闭的本地模式语音提示。
- 默认关闭的直接语音翻页命令。

验收：

- 所有能力均由编译开关控制，默认关闭。
- 音频、语音功能失败不影响核心码表显示。
- 语音翻页只作为交互验证，不承诺完整语音助手。

## 阶段 5：云 AI 和云音乐探索

状态：远期探索。

目标：

- 评估设备直连云 AI 服务。
- 评估云音乐流播放。
- 定义不绑定单一供应商的 AI 接口。

验收：

- 录音必须由用户主动触发。
- 云能力不可成为核心码表功能依赖。
- 网络或服务失败时，速度、电量、页面切换继续可用。
- 仓库不包含 API token、Wi-Fi 密码或个人数据。

## 当前优先级

1. 稳定 `src/firmware/bikemb` 的 LVGL dashboard。
2. 保持 `src/firmware/bringup` 作为安全硬件验证入口。
3. 接入可替换的数据模型，为真实轮速、电量和持久化数据做准备。
4. 在核心码表稳定后再推进音频、语音和云 AI 实验。
